## TL;DR

- EKS 클러스터 11개가 1.31부터 1.34까지 제각각의 버전에 멈춰 있었습니다. 노드 오토스케일러(Karpenter)는 가장 낡은 곳이 v0.33이었습니다. 최신과는 API 세대(v1beta1/v1)가 갈리는 격차였습니다. 지원 종료는 다가오는데 2024년 실측 기준 한 클러스터 한 버전에 약 6주가 걸리던 작업입니다.
- 8일(2026-07-01~08) 동안 전 클러스터를 1.35로, Karpenter를 1.9로, 노드 OS를 Bottlerocket으로 통일했습니다. 상시 노드 약 420대가 단계마다 전부 교체됐고 고객 트래픽을 받는 운영 메인(노드 222대)의 1.31→1.35 구간은 19시간 17분이 걸렸습니다. 서비스 중단은 없었습니다.
- 방법은 역할의 재배치였습니다. AI 에이전트가 정찰·변경 초안·검증 루프를 맡아 8일간 PR 109건을 만들었고 사람은 그 전부의 머지·적용 승인 게이트를 지켰습니다. 무거운 결정은 서로 다른 AI 두 개(Claude·Codex)를 토론시켜 교차검증했고 최종 판정은 언제나 측정 데이터에 맡겼습니다.
- 함정이 세 번 있었습니다. 세 번 모두 서비스가 아니라 절차 안에서 터졌습니다. 무중단은 운이 아니라 실패해도 되는 곳에서만 실패하도록 만든 설계의 결과였습니다.

## 6주의 기억, 그리고 열한 개의 클러스터

2024년 상반기, 저희는 메인 클러스터를 쿠버네티스 1.29로 올렸습니다. 착수 커밋부터 마무리 머지까지 약 6주. 특별히 느렸던 게 아닙니다. 호환성 매트릭스를 사람이 읽고 변경을 사람이 만들고 검증을 사람이 돌면 그 정도가 걸립니다. 6주짜리 작업은 연간 계획에서 자꾸 밀립니다. 밀린 결과가 올해의 출발선이었습니다.

2026년 6월 말 기준, 저희 EKS 클러스터 11개의 상태는 이랬습니다.

| 클러스터 용도 | K8s 버전 | Karpenter |
| --- | --- | --- |
| 데이터 파이프라인 (dev/prod) | 1.34 / 1.33 | 1.6 / v0.33 |
| DB 운영 (dev/prod) | 1.32 / 1.32 | 1.5 / 1.5 |
| 내부 도구 (dev/prod) | 1.34 / 1.34 | 1.6 / 1.6 |
| 보안 허브 | 1.34 | 1.6 |
| 웹 서빙 (dev/prod), 스테이징 | 1.35 | 1.5 ⚠️ (1.35 미지원) |
| 개발 메인 (98노드) | 1.31 | 1.0 |
| 운영 메인 (222노드, 고객 트래픽) | 1.31 | 1.0 |

버전이 밀리는 이유는 게으름이 아니라 두려움입니다. 컨트롤플레인을 올리는 것 자체는 버튼 하나입니다. 무서운 건 그다음입니다. 노드를 전부 갈아야 하고 노드를 갈면 그 위의 파드가 전부 이사를 다닙니다. 오토스케일러가 새 버전을 지원하는지, CRD가 깨지지 않는지, 상태를 가진 워크로드가 재기동을 견디는지. 확인할 것이 클러스터마다 다르고 저희는 그런 클러스터가 열한 개였습니다. 가장 낡은 데이터 클러스터의 Karpenter는 v0.33, API 세대가 v1beta1에서 v1로 갈리는 협곡을 통째로 건너야 하는 버전이었습니다.

예전 방식대로면 이건 분기 단위 프로젝트입니다. 저희가 바꾸고 싶었던 건 이번 업그레이드 한 번이 아니라 **업그레이드가 무겁지 않은 팀이 되는 것**이었습니다.

## 원칙: 속도는 생략이 아니라 반복에서 나온다

착수 전에 원칙을 고정했습니다. 빠르게 가되, 빨라지는 방법은 절차의 생략이 아니라 절차의 반복 가능화여야 했습니다.

**한 번에 한 마이너씩.** 1.31에서 1.35로 건너뛰지 않습니다. 컨트롤플레인은 1.32, 1.33, 1.34, 1.35를 차례로 밟고 각 단계에서 노드와 애드온(coredns, kube-proxy, CNI)을 함께 맞춥니다. 문제가 생겨도 어느 계단에서 생겼는지가 분명해집니다.

**선행 조건부터 역순으로.** 각 쿠버네티스 버전에는 그것을 지원하는 Karpenter 최소 버전이 있습니다(1.34는 1.6 이상, 1.35는 1.9 이상). 노드를 올리기 전에 오토스케일러를, 오토스케일러를 올리기 전에 IAM 권한과 CRD를 먼저 맞췄습니다. 이 순서를 어기면 새 노드가 아예 뜨지 못하는 구간이 생깁니다.

**개발 클러스터가 항상 먼저.** 같은 유형의 dev에서 전체 절차를 한 번 통과시켜 패턴을 검증한 뒤, 그 패턴을 prod에 그대로 반복했습니다. 파일럿 없이 prod을 만진 클러스터는 하나도 없습니다.

**상태 있는 것은 얼려두고, 마지막에 통제된 창에서.** 그래프 DB, 로그 분석 DB(ClickHouse), 단일 replica 도구처럼 재기동이 아픈 워크로드는 노드 교체 대상에서 먼저 제외했습니다(disruption budget 0). 나머지를 전부 끝낸 뒤 담당 팀과 조율한 창에서 순서대로 옮겼고 옮기지 않기로 한 것(수명이 정해진 ClickHouse 노드 13대)은 끝까지 옮기지 않았습니다.

**매 단계 같은 검증.** 노드 버전과 시스템 컴포넌트 상태만 보지 않습니다. 클러스터 안 전체 파드의 상태(비정상·재시작 카운트)와 워크로드 로그(에러 레벨·5xx)까지, 매 단계 같은 기준으로 확인했습니다. 이 체크리스트는 8일 동안 수십 번 반복됐고 한 번도 생략되지 않았습니다.

노드 교체의 안전판은 두 겹이었습니다. 관리형 노드그룹은 새 노드가 준비된 뒤에만 기존 노드를 비우는 서지(surge) 방식이고 Karpenter 풀은 동시에 교체 가능한 노드 수를 disruption budget으로 묶었습니다. 여기에 PodDisruptionBudget과 강제 분산(topology spread)이 겹칩니다. 어느 층에서든 "새것이 서기 전에 옛것이 사라지는" 순간은 구조적으로 만들 수 없게 해뒀습니다.

## AI에게 무엇을 맡기고, 무엇을 맡기지 않았나

이번 작업의 진짜 실험은 업그레이드 자체보다 **운영 모델**이었습니다. AI 에이전트(Claude Code)를 질문에 답하는 도구가 아니라 오퍼레이터로 썼습니다.

**AI가 맡은 일: 반복과 정찰.** 클러스터 현황 정찰(버전·노드·애드온·호환성 매트릭스 작성), 변경 PR 초안, 적용 후 검증 루프(노드 버전, 전체 파드 상태, 로그 스캔), 그리고 이 모든 과정의 기록. 8일간 세 개 저장소에 걸쳐 **PR 109건**이 이렇게 만들어졌습니다. 사람이 하면 클러스터당 반나절씩 걸리던 확인 노동이 분 단위로 줄었다는 것보다 중요한 건, 열한 개 클러스터를 도는 동안 같은 체크리스트가 단 한 번도 생략되지 않았다는 점입니다. 사람은 반복에서 실수하고 에이전트는 반복에서 지치지 않습니다.

**사람이 쥔 것: 관문.** PR 109건 전부가 사람의 머지 승인을 거쳤고 프로덕션 적용(IaC apply, 수동 sync)은 그와 별도의 승인 게이트를 한 번 더 지났습니다. GitOps와 IaC 위에서 작업했기에 이 게이트는 자연스럽게 PR과 apply 지점에 걸립니다. AI가 아무리 확신해도 변경이 실제 클러스터에 닿는 관문은 사람이 지켰습니다. 상태 있는 워크로드의 이동 창을 언제 열지, 인시던트에서 여러 해법 중 무엇을 택할지도 사람의 몫이었습니다. 요약하면 **판단의 속도는 AI가 올리고 판단의 권한은 사람이 갖는다**입니다.

**AI는 AI로 반박시켰습니다.** 결정이 무거울수록 하나의 모델이 낸 결론을 그대로 믿지 않았습니다. 여기서 쓴 도구가 인프라팀 DBA 선상원 님이 만든 **AI 협업 프로토콜**입니다. 서로 다른 두 AI(Claude와 Codex)를 파일 기반 라운드 방식으로 연결해, 한쪽이 설계하면 다른 쪽이 데이터를 들고 반박하고 그 왕복이 전부 기록으로 남는 구조입니다. 이번 업그레이드의 무거운 결정들은 전부 이 프로토콜 위에서 토론을 거쳤고 토론은 실제로 결론을 바꿨습니다. 한 예로, 노드 교체 시 게이트웨이의 종료 유예(preStop) 값을 정할 때 한쪽이 일반론에 기대 "60~90초가 필요하다"고 추정하자 반대쪽 검토를 거쳐 개발 환경에서 실측을 돌렸습니다. 측정된 실제 전파 시간은 **최악 9.5초**. 설정값은 실측의 2배 마진인 20초로 확정됐습니다. 혼자 결론 내리고 밀어붙이는 대신 AI 둘이 근거를 들고 논쟁하는 걸 지켜보다 갈라지는 지점만 사람이 판정한다. 이 형식의 힘은 추정끼리 합의하는 게 아니라 **측정이 추정을 이기는 구조**를 강제한다는 데 있습니다. 팀원이 만든 프로토콜이 팀의 표준 작업 방식이 되어가는 과정이기도 합니다.

마지막 조각은 **연속성**입니다. 진행 상황을 체크포인트 문서와 장기 메모리에 계속 남겨, 세션이 끊겨도 "어디까지 했더라"에서 다시 시작하지 않게 했습니다. 8일짜리 작업은 실제로는 여러 번의 세션으로 쪼개져 있었지만, 기록 덕에 한 번의 흐름처럼 이어졌습니다.

## 8일의 여정

![](attachment:878557d9-f741-4503-9873-4ed60dbcb3ec:timeline.png)

**1~2일차: 함대 아홉.** 데이터·DB·내부 도구·보안 허브·웹 클러스터 아홉 개를 이틀에 1.35로 맞췄습니다. dev에서 패턴을 검증하고 prod에 반복하는 리듬입니다. 첫 파일럿(데이터 dev)에서 절차가 확립됐습니다. Karpenter 1.9 선행(CRD·IAM 포함), 컨트롤플레인 스텝업, 애드온 정렬, 전 파드 검증. 이 절차가 이후 모든 클러스터의 템플릿이 됐습니다. 보안 허브처럼 예민한 곳은 접근 통제 도구가 올라간 노드 풀을 먼저 얼려 교체 대상에서 빼두고 진행했습니다. 가장 낡은 데이터 클러스터는 Karpenter v0.33에서 1.9까지, API 세대를 건너는 풀 마이그레이션을 여기서 치렀습니다(5장).

**3일차: 개발 메인.** 노드 98대짜리 개발 메인을 1.31에서 1.32로 올리며 레거시 구간의 절차를 확립했습니다. 이 클러스터는 수작업 시대의 IaC와 GitOps가 섞인 하이브리드라 어디가 어느 도구의 관할인지부터 지도를 그려야 했습니다. 이후 이틀에 걸쳐 1.35까지 마저 올렸습니다.

**6~7일차: 운영 메인, 19시간 17분.** 고객 트래픽을 받는 운영 메인(노드 222대)을 1.31에서 1.35로 올렸습니다. 컨트롤플레인 업그레이드 시작부터 마지막 노드 교체 완료까지 **19시간 17분**. 각 버전 계단마다 컨트롤플레인을 올리고 곧바로 그 버전의 노드로 전부 교체하는 것을 네 번 반복했고 그 사이 게이트웨이·인증·결제·커머스 워크로드는 계속 트래픽을 받았습니다. 트래픽이 가장 민감한 게이트웨이 풀은 카나리 노드 한 대로 시작해 정상을 확인한 뒤에야 나머지를 순차로 밀었습니다.

눈여겨볼 대목은 노드 OS 전환의 상당 부분이 이 안에 **합승**했다는 점입니다. 인증·게이트웨이를 포함한 여러 풀이 1.32 계단에서 버전 교체와 동시에 Bottlerocket으로 넘어갔습니다. 어차피 노드를 전부 갈아야 한다면 한 번의 교체에 두 개의 변화를 싣는 편이 총 교체 횟수를 줄입니다. 물론 이것도 파일럿 풀 하나로 먼저 검증한 뒤의 얘기입니다.

**7~8일차: Bottlerocket 마무리.** 남은 대형·특수 풀을 전환했습니다. Bottlerocket은 컨테이너 실행에 필요한 것만 남긴 불변 OS로, 루트 파일시스템이 읽기 전용이라 노드에 들어가 손댈 여지 자체가 작습니다. SSH 없이 운영하는 저희 방향(이전 글)과 정확히 맞물립니다. 두 곳이 까다로웠습니다. CI 러너 풀은 privileged docker-in-docker가 불변 OS 위에서 도는지를 파일럿 노드에서 빌드·실행·풀까지 실측으로 확인한 뒤 넘겼고 OS/데이터 볼륨이 분리되는 디스크 구조 차이는 러너 캐시 용량을 맞춰 흡수했습니다. 모니터링 풀은 같은 노드 클래스를 ClickHouse가 공유하고 있어 DB 쪽 정의를 건드리는 대신 **모니터링 풀을 새 노드 클래스로 떼어내는 역방향**을 택했습니다. 재기동이 아픈 쪽은 손대지 않는다는 원칙의 연장입니다.

8일이 끝났을 때 클러스터 11개 전부 1.35, Karpenter 전부 1.9, 노드 OS는 ClickHouse 노드 13대(fade-out 예정)를 제외한 dev·prod 전체가 Bottlerocket이 됐습니다.

## 함정의 해부: 세 번 갇혔고 세 번 다 서비스 밖이었다

**갇힘 1: 저장된 과거가 미래를 막다.**

데이터 클러스터에서 Karpenter API를 v1 전용으로 전환한 직후, 컨트롤러가 기동 불능에 빠졌습니다. 원인은 미묘했습니다. 전환 전에 안전을 위해 노드들을 얼려뒀는데 그 얼어 있던 노드들의 리소스 객체가 etcd에 **구세대(v1beta1)로 물리 저장**된 채 남아 있었던 겁니다. CRD가 v1 전용이 되는 순간 이 객체들은 읽기 불가가 됐고 목록 조회가 실패하자 컨트롤러의 캐시 동기화가 시작 단계에서 멈췄습니다. 해법은 쿠버네티스의 정석인 storage version migration입니다. 구버전 읽기를 임시로 다시 열고 객체를 하나씩 다시 써서 v1로 재저장한 뒤 다시 닫았습니다. 교훈은 두 줄입니다. **API 세대를 닫기 전에 저장된 모든 객체가 새 세대로 읽히는지 전수 확인할 것**(`kubectl get --raw`). "안전을 위한 동결"이 마이그레이션보다 먼저 오면 얼어붙은 객체가 나중에 발목을 잡는다는 것. 이 시간 동안 그래프 DB는 얼려진 노드 위에서 무손상으로 돌았습니다. 갇힌 건 컨트롤러였지, 서비스가 아니었습니다.

**갇힘 2: 선언과 현실의 불일치.**

선언형 컨트롤러(ACK)로 관리하는 클러스터에서, 노드그룹의 버전 필드는 올렸는데 자동으로 채워지는 AMI 릴리스 버전 필드가 구버전을 가리키는 어긋남이 생겼습니다. GitOps 화면은 "정상 동기화"인데 실제 업그레이드는 두 시간째 실행되지 않는 상태였습니다. 선언이 현실과 어긋나면 컨트롤러는 조용히 멈춥니다. AWS API를 직접 호출해 롤을 진행시키고 완료 후 선언 값을 실제 값으로 되맞춰 정합을 회복했습니다. 이후 클러스터부터는 컨트롤플레인이 ACTIVE가 되는 즉시 노드그룹 업그레이드를 직접 트리거하는 것을 표준 절차에 넣어, 같은 대기가 재발하지 않게 했습니다. 함정 하나가 절차 한 줄이 된 셈입니다.

**갇힘 3: 전환 도구 자체의 결함.**

v1beta1에서 v1로 넘어가는 길목의 중간 버전에는 conversion webhook의 알려진 결함이 있었습니다(컨트롤러가 인증서와 어긋나는 설정을 90초마다 되쓰는 문제). 이건 만나서 대응한 게 아니라 사전 조사에서 알고 들어갔고 해당 버전에 머무는 시간을 최소화하고 다음 버전으로 곧장 탈출하는 경로를 미리 설계에 넣었습니다. 알려진 함정은 밟는 시간을 줄이는 것이 최선의 대응입니다.

세 번의 갇힘에는 공통점이 있습니다. 상태 있는 워크로드는 얼려져 있었고 안전판(budget·surge·PDB)은 켜져 있었고 그래서 갇힌 범위가 항상 절차 안이었다는 점입니다.

## 지금은 사람이 용기를 내는 단계, 다음은 에이전트가 먼저 움직이는 단계

이번에 확인한 것은 세 가지입니다.

첫째, **속도와 안전은 교환 관계가 아니었습니다.** 빠를 수 있었던 이유(같은 절차의 반복, 매 단계 같은 검증, 실패 허용 구간의 사전 설계)가 곧 안전할 수 있었던 이유였습니다.

둘째, **AI는 오퍼레이터로 쓸 때 값이 컸습니다.** 정찰하고 초안을 만들고 검증 루프를 도는 실행자로 쓰되 관문은 사람이 지키고, AI의 추정은 다른 AI로 반박시키고, 최종 판정은 측정에 맡기는 구조. 이 구조가 팀원에게 번지기 시작했다는 점이 개별 성과보다 값집니다.

셋째, 업그레이드는 이제 저희에게 프로젝트가 아니라 **루틴**입니다. 다만 정확히 말하면, 지금 단계는 "정리된 정책과 가드레일 덕에 **사람이 용기를 낼 수 있게 된**" 단계입니다. 검증된 절차·안전판·기록이 있으니, 이 작업을 제가 아닌 다른 팀원이 잡아도 짧은 시간 안에 무중단으로 완주할 수 있습니다. 그것만으로 6주는 8일이 됐습니다.

다음 단계는 방향이 다릅니다. 사람이 절차를 따라가는 게 아니라 **에이전트가 정리된 절차를 스스로 인식하고 먼저 움직이는 것**입니다. 새 버전이 나오면 에이전트가 알아서 dry-run과 호환성 검증(오토스케일러·CRD·애드온 매트릭스)을 돌려두고, 클러스터 우선순위에 따라 점진 업그레이드 계획을 세워 승인만 기다리며, 적용 중에는 실시간 모니터링과 이슈 대응·롤백 준비까지 함께 서 있는 형태. 사람의 역할은 절차의 수행자에서 계획의 승인자로 한 칸 더 물러납니다. 이번 8일은 그 단계로 가기 위한 절차의 표준화이기도 했습니다.
